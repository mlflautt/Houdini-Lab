## Delivered API and schema

Lane D provides the pure API:

```text
build_project_index(project: Mapping, plan: Mapping, *,
                    project_root: str | Path | None = None,
                    runtime_identity: Mapping | None = None,
                    execution_records: Iterable[Mapping] = (),
                    artifacts: Iterable[Mapping] = ()) -> dict
```

The result schema is `hermes.houdini.project_index.v1`. It contains canonical source, plan, and
index hashes; ordered variants and topological stages; contract producers/consumers; checkpoints;
explicit artifacts and optional integrity results; evidence grouped independently by graph, data,
pixel, plugin, model, human, and downstream rungs; approvals; human decision slots and explicit
append-only human records; warnings, blockers, rejected lineage, compatibility drift, separate
mechanical/human statuses, and disabled automatic execution/ranking.

`index_sha256` excludes only itself. It retains pending, rejected, non-applicable, and blank-human
lineage. Execution/artifact caller order and mapping key order do not change the hash; semantic stage
and variant order remains hash-significant.

## Drift and evidence routing

Structured drift categories are:

- `houdini_build`
- `license`
- `package`
- `optional_dependency`
- `capability_adapter_identity`
- `source_hash`
- `artifact_integrity`

Unknown, duplicate, or source/plan-hash-mismatched stage records are structured blockers. No
duplicate is chosen by input order. Missing execution is `pending`. The five G001 states remain
distinct; required `not_applicable` evidence remains pending unless its whole stage was explicitly
declared non-applicable with a concrete reason. Mechanical aggregation never promotes model, human,
or downstream status. A winner, rating, feedback, or continuation value can enter only through an
explicit stage-bound human record; dry variants and decisions must remain null.

## Artifact confinement and hash proof

The observer consumes only caller-supplied artifact mappings and never walks a directory. Without
`project_root`, metadata is preserved and no path operation is performed. With an explicit absolute
root, paths must be absolute and lexically confined. Byte access still requires `verify: true`; that
mode resolves both root and file, rejects symlink escape, requires a claimed SHA-256, hashes the
file, and reports size. `durable: true` requires SHA-256 even when byte verification is deferred.

Focused tests prove:

- metadata-only construction remains successful while `Path.open`, `resolve`, `is_file`, and `stat`
  are monkeypatched to fail on any hidden discovery;
- relative and outside-root paths become structured blockers;
- a supplied file remains `not_checked` by default, passes only after explicit byte verification,
  and becomes `artifact_hash_mismatch` when its claimed hash differs;
- reversed record/artifact order and reordered mapping keys produce the same `index_sha256`.

No durable non-Git artifact was created. Pytest used only its disposable temporary directory for the
opt-in file-integrity fixture.
